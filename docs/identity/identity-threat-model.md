# Identity & Multi-Tenancy Threat Model — Phase 2

**Document ID:** IDENT-009 | Version 1.0 | Status: Draft for Approval | Phase: 2A (Architecture Finalization)

Extends `THREAT_MODEL.md` (SEC-002) for the identity/multi-tenancy surface specifically.
Every threat below maps to a control already specified in `authorization.md`,
`multi-tenancy.md`, `authentication.md`, or `identity-sync.md` — this document does not
invent new controls, it indexes the ones already designed against specific attacks and adds
detection/test requirements.

| 5   | **Forged workspace IDs**                                | Client sends a workspace ID in a header/body/query param that does not match their actual authorized context, attempting to widen scope.                                                                                     | The active workspace context is server-resolved (`workspace-model.md` §3), never taken at face value from a request field; a mismatched claim fails `requireMembership()` like any other unauthorized attempt.                                                                                                                                                                                                                                                                              | Same as #1/#4.                                                                                                                                                                                                                                              | Send requests with a workspace ID field that differs from the server-resolved active workspace; assert the server-resolved value (or rejection), never the client-supplied one, governs the outcome.                                             |

| 12  | **AI prompt injection attempting authorization bypass** | Malicious text in a campaign name, ad creative, or user message attempts to instruct the AI to "act as admin," "ignore permissions," or otherwise induce a tool call outside the user's actual permissions.                  | AI never holds authorization itself — every tool call re-runs the full chain using the initiating user's real, current permissions (`authorization.md` §6); external content is untrusted data, never instructions (`AI-007`, `ADR-002-AI-EXECUTION-BOUNDARY`).                                                                                                                                                                                                                             | Tool-call audit trail shows the actual permission check result per call, independent of what the model "believed" it was doing — a mismatch between model intent and enforced outcome is expected and correct, not a bug to fix by trusting the model more. | Construct a prompt-injection payload instructing the AI to bypass a permission check or act with elevated privilege; assert the underlying `requirePermission()` call still denies exactly as it would for a direct API call from the same user. |
| 13  | **Webhook forgery**                                     | An attacker sends a fake Clerk webhook payload (e.g. a forged `user.updated` or `organizationMembership.updated`) to our endpoint to manipulate application state.                                                           | Signature verification via `verifyWebhook()` before any processing (`identity-sync.md` §2 step 1) — an unsigned or invalid-signature request is rejected before touching any data.                                                                                                                                                                                                                                                                                                          | Failed-verification attempts logged distinctly from valid-but-unprocessable events.                                                                                                                                                                         | Send a payload with an invalid/missing signature; assert rejection with no state change, and no information disclosure distinguishing "bad signature" from other failure modes in the response body.                                             |
| 14  | **Replayed webhook**                                    | A previously valid, correctly signed webhook event is captured and re-sent later to re-trigger its effect (e.g. re-applying an old role/state change).                                                                       | Event-ID-keyed idempotency (`identity-sync.md` §2 step 6) — a duplicate event ID is a no-op regardless of signature validity, since a valid old signature does not imply the event should be reprocessed.                                                                                                                                                                                                                                                                                   | Duplicate event IDs observed are logged as a "duplicate, no-op" outcome distinctly from a first-time processed event, for audit clarity.                                                                                                                    | Re-submit a previously processed, validly signed event; assert no state change occurs the second time.                                                                                                                                           |
| 15  | **User deletion synchronization failure**               | A Clerk user is deleted, but the corresponding webhook is missed/delayed/fails, leaving the user able to continue acting in our system indefinitely via a still-valid session, or leaving orphaned audit/action attribution. | Reconciliation pass (`identity-sync.md` §4) as backstop against missed webhooks; session validity is still checked live via Clerk per request (`authentication.md` §2 "Session expired/revoked" — Clerk itself invalidates the deleted user's sessions, independent of our webhook processing), so the _authentication_ half of this fails safely even if our _database sync_ is delayed; the _data_ half (orphaned attribution) is handled per `identity-sync.md` §User Deletion Handling. | Reconciliation pass reports any Clerk-side-deleted user still marked active in our database as a discrepancy requiring attention.                                                                                                                           | Simulate a missed `user.deleted` webhook (do not deliver it) and confirm (a) the user cannot authenticate once Clerk itself invalidates their session regardless, and (b) the next reconciliation pass detects and corrects the local state.     |

## Security Invariants (identity-specific, extending SEC-002 §Security Invariants)

- No request crosses a workspace boundary, regardless of which layer (API, worker, AI
  tool, report, audit read) it originates from.
- No client-supplied identifier (workspace ID, resource ID, role, permission) is ever
  authorization-sufficient on its own — a database check always follows.
- No webhook event is processed without signature verification, and no event is processed
  more than once to completion.
- No AI tool call executes with any permission the initiating user does not actually,
  currently hold.
