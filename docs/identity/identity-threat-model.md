| 16  | **Self-service role/permission escalation**                   | A member with `members.update` (ADMIN) attempts to assign themselves or another member a higher-authority role than the caller should be able to grant, including OWNER, via a role-change endpoint.                                                                                                                                                                    | `rbac.md` §8: `changeMembershipRole()` must reject `newRole === "OWNER"` unconditionally (OWNER assignment only via `transferOwnership()`); self-mutation (`actor.userId === target.userId`) is blocked outright for every role-mutation call; MANAGER/ANALYST/VIEWER hold no `members.update` at all, so the check is unreachable by them regardless.                                                                                                              | An unexpected `role_changed` `AuditEvent` where `actorId === target userId`, or a `newRole: OWNER` value ever reaching `changeMembershipRole()`, is a hard logic error, not a permitted-but-unusual case.                                                                                                                    | Attempt every combination: ADMIN assigns OWNER to self; ADMIN assigns OWNER to another member; ADMIN assigns any role to self; assert all rejected before any DB write.                                                                                                                                                                                                                         |

## Security Invariants (identity-specific, extending SEC-002 §Security Invariants)

- No request crosses a workspace boundary, regardless of which layer (API, worker, AI
  tool, report, audit read) it originates from.
- No client-supplied identifier (workspace ID, resource ID, role, permission) is ever
  authorization-sufficient on its own — a database check always follows.
- No webhook event is processed without signature verification, and no event is processed
  more than once to completion.
- No AI tool call executes with any permission the initiating user does not actually,
  currently hold.
- **(Phase 2.4A)** No role mutation may assign OWNER outside `transferOwnership()`'s atomic
  swap, and no membership may change its own role.
- **(Phase 2.4A)** No authorization primitive fails open — every non-success path is an
  explicit throw/deny, never an implicit pass-through.
- **(Phase 2.4A)** No authorization-relevant mutation (role, membership, ownership,
  workspace lifecycle) commits without its `AuditEvent` committing in the same transaction.
