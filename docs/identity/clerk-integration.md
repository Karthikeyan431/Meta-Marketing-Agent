## 2. Integration Pattern (design only — not implemented this phase)

```text
Browser
  ↓  (Clerk-issued session JWT, HttpOnly cookie)
apps/web  — <ClerkProvider> (App Router, inside <body>)
  ↓
middleware.ts — clerkMiddleware()   [Next.js 15.x filename]
  · establishes req.auth (userId, sessionId, orgId if active)
  · does NOT authorize anything — see finding #3
  ↓
apps/api — Route Handlers / Server Actions
  ↓
Our requireAuth() / requireWorkspace() / requireMembership() / requirePermission() / requireResourceAccess()
  (application-owned — see authorization.md; NOT Clerk has()/auth.protect() alone)
  ↓
PostgreSQL — workspace-scoped query
```

- Clerk issues and validates the **session** and gives us a stable **Clerk user ID** (`clerkUserId`). It is the identity/session provider only.
- Clerk **Organizations** are used only as a convenience mirror of workspace membership for Clerk's own UI components (organization switcher, invitation UI) if used — **the application's Workspace/Membership/Role/Permission tables in our own database are the sole authorization source of truth.** A Clerk Organization ID may be stored on our `workspaces` row as a foreign reference, never as an authorization check.
- Clerk secret key (`CLERK_SECRET_KEY`) and webhook signing secret (`CLERK_WEBHOOK_SIGNING_SECRET`) are server-only environment variables. **Never exposed to the browser** — only `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY` is client-safe, consistent with `ENCRYPTION_SECRETS.md` (SEC-011) and `CLAUDE.md`'s "never expose secrets" rule.
